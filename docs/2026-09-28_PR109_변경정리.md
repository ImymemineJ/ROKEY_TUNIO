## 1. 취소 · 일시정지 · 재개 (#106)

### 1.1 버튼이 하는 일

- **일시정지** — 움직이던 팔에 두산 `MovePause` 를 보내 그 자리에서 멈춘다. 그다음 이동과 그리퍼 명령도 막는다.
  - 로봇이 "멈췄다" 고 확인해 줘야 웹이 '일시정지' 로 바뀐다. 확인 전에는 바뀌지 않는다.
- **재개** — 로봇 상태가 정상인지 보고 `MoveResume` 으로 **남은 이동을 잇는다.** 같은 이동을 처음부터 다시 보내지 않는다.
  - 일시정지 동안 녹음하던 측정은 버리고, 재개 뒤 발현 준비부터 다시 한다. 이건 측정 실패 횟수에 들어가지 않는다.
- **취소** — Soft Stop(`MoveStop`)으로 멈추고, 정말 멈췄는지(`CheckMotion` = 대기) 확인한 뒤 작업을 끝낸다. 자동으로 홈에 돌아가지 않는다.
  - **취소한 뒤에는 로봇 노드(robot_controller)를 다시 켜야 새 동작을 받는다.** 현장 상태(피크를 쥐고 있는지, 기타에 닿아 있는지)를 사람이 확인하라는 뜻의 안전장치다.

### 1.2 9/23 실기에서 무엇이 실패했나

- 일시정지를 누르자 "일시정지/재개 서비스 미연결" 로 작업이 **통째로 오류 종료**됐다.
  - 서비스 목록에는 보였는데, 확인하는 그 순간에만 연결이 안 잡혀 있었다. PC 두 대 사이에서는 이런 틈이 생긴다.
  - 코드가 연결을 **딱 한 번만** 보고 포기했다.
- "register_peg goal 거부" 가 떴는데 **왜 거부했는지 관제에서 알 방법이 없었다.**
- 취소도 바로 먹지 않았다.

### 1.3 고친 것

관제(서버) 쪽
- 로봇 일시정지/재개 서비스 연결을 **최대 5초 기다리면서** 확인한다.
- **요청이 로봇에 닿지도 못했으면 거절만 한다.** 작업은 그대로 진행된다(일시정지 실패) / 일시정지 상태가 유지된다(재개 실패). 사용자는 다시 누르거나 취소하면 된다.
  - 요청이 **닿았는데** 로봇이 거부하거나 응답이 없으면, 로봇 상태를 모르는 것이라 안전하게 취소로 넘어간다.
- 로봇이 보내는 거부 사유(`/robot/notice`)를 받아 오류 문구에 붙인다. 예: `register_peg goal 거부 (로봇: 새 동작 거부 — 취소/제어 실패 후 현장 복구 확인·robot_controller 재시작 필요)`
- 마이크 준비(ready) 기다리는 중에도 취소를 본다. 전에는 최대 10초 늦게 반응했다.

로봇 쪽
- 동작 요청을 받을 때 두산 정지 서비스 연결을 **최대 2초 기다린다** (`service_wait_sec`). 없으면 이유를 붙여 거부한다.
- 거부·잠금 이유를 `/robot/notice` 로 관제에 보낸다.
- 취소 시 정지 명령 전 연결 확인도 **제한 시간(5초) 안에서 다시 확인한다.** (Docker 테스트로 찾은 것, 5절)

### 1.4 알아 둘 한계

- **발현 스트로크(피크가 줄을 긁는 짧은 구간) 중에 누르면 스트로크가 끝난 뒤 멈춘다.** 두산의 비동기 이동 명령이 곡선 보간을 지원하지 않아 그 구간만 예전 방식으로 남겼다.
- **힘 제어 중에는 일시정지가 정지(취소)로 바뀐다.** 힘을 주고 있는 자세는 멈춘 채 유지된다는 보장이 없어서다.
- 이 기능은 **소프트웨어 제어**다. 비상정지 버튼을 대신하지 않는다.
- 일반 이동을 "보내고 → 끝났는지 확인" 방식으로 바꿨다. 두산 드라이버가 이동 중에는 일시정지 요청을 처리하지 못해서다. 목표 도달 허용 오차 0.5mm / 0.1도는 실측 전 임시값이다.

## 2. #88 피크 보충 대기와 관제 연결

### 2.1 #88 이 하는 일 (로봇 단독으로는 확인됨)

- 그리퍼 폭으로 피크를 쥐었는지 본다. 거치대에서 집은 직후, 줄을 튕기고 물러난 뒤, 재개 직후에 본다.
- 없으면 거치대에서 **재집기를 2번** 더 해 본다.
- 그래도 없으면 **홈으로 돌아가 멈추고** 사람이 피크를 채워 주길 기다린다.

### 2.2 관제와 합칠 때 생긴 문제

#106 이 들어오면서 "멈춤" 이 두 종류가 됐는데, 둘 다 화면에는 '일시정지' 로 보인다.

- **로봇 일시정지(#106)** — 사람이 버튼을 눌러 **움직이던 팔을 멈춘** 것. 재개하려면 로봇에게 `MoveResume` 을 보내야 한다.
- **피크 보충 대기(#88)** — 로봇이 **홈 복귀까지 끝내고 할 일이 없는** 상태. 로봇 쪽에는 멈춘 동작이 없다.

그대로 합쳤으면 보충 대기 중 재개를 눌렀을 때 관제가 로봇에게 "재개해" 를 보내고, 로봇은 "멈춘 게 없다" 며 거부하고, #106 규칙상 **작업이 취소로 넘어갔다.**

### 2.3 해결

- 관제가 지금 어떤 멈춤인지 따로 기억한다.
- **보충 대기에서 재개** → 로봇을 부르지 않고 관제 안에서 바로 풀고, 같은 줄의 발현 준비부터 다시 한다.
- **로봇 일시정지에서 재개** → 예전처럼 로봇에게 `MoveResume` 을 보내 확인받고 푼다.
- 두 경우 모두 다음 발현 준비 요청에 **"재개됐음"(`resumed=true`)** 을 실어 보낸다. 로봇은 이걸 보고 **피크가 아직 있는지 다시 확인**한다.
- 웹에 **호박색 "로봇 알림" 띠**가 뜬다. 예: `피크 재집기 2회 모두 빈손 — 홈 복귀 완료. 피크를 거치대에 꽂고 재개를 누르세요`

### 2.4 알아 둘 것

- 피크 확인은 **재개하는 그 순간이 아니라 다음 발현 준비 때** 한다. 멈췄던 동작은 먼저 끝까지 간다.
- **보충 대기 중에 취소하면** 로봇에 '보충 대기' 상태가 남아 재등록까지 거부된다. 로봇 노드를 다시 켜면 풀린다. (#106 의 "취소 후 로봇 노드 재시작" 과 같은 절차)
- 실제 ROS 로 "피크 없음 → 홈 → 보충 대기 → 웹 재개 → 다시 측정" 과 "보충 대기 중 취소" 를 24가지 조합으로 돌려 통과했다(가짜 로봇 동작). 실물 로봇으로는 아직이다.

## 3. 관제 웹 개편 (#107)

**쓰는 법은 그대로다.** 실행 명령, 주소, 버튼, 서버 API 가 같다. 화면 파일만 바꿨다. FastAPI 버전이 아니라 기존 방식(web_node 안의 http.server + SSE)이다.

### 3.1 화면 구성

- **기타 그림** — 기타 전체 그림 위에 줄과 페그 위치를 겹쳐 그렸다. 좌표는 그림에서 직접 재서 맞췄다.
  - 헤드에 커서를 올리면 헤드가 확대된다. 🔍 버튼으로 확대를 고정한다.
  - 4·3번 줄은 조율하지 않아 점선으로 흐리게 보인다.
- **튜너** — 반원 게이지(±50센트)에 지금 오차를 바늘로 보여 준다. 양 끝에 ♭(낮음) ♯(높음) 표시. 큰 음이름, 센트, 측정 → 목표 Hz.
- **예상 페그 회전** — 지금 오차면 페그를 몇 도 돌릴지 보여 준다. 예: `풀기 42.4° → 조임 28.2°`
  - task_manager 가 실제로 쓰는 계산 함수(`tuning_logic.adjust_plan`)를 그대로 불러서, 화면 숫자와 로봇이 돌리는 각도가 같다.
  - 음이 높으면 "풀기 → 조임" 두 단계가 나온다. 백래시 때문에 목표 아래로 풀었다가 조여 올리는 규칙(CLAUDE.md 3.2) 그대로다.
  - 회전 방향 화살표는 뺐다. 3+3 헤드는 왼쪽(6·5·4)과 오른쪽(3·2·1) 페그의 조이는 방향이 반대라 화살표 하나로 맞게 그릴 수 없다.
- **줄별 진행** — 6·5·2·1번이 **세로 블록 4개**로 나란히. 지금 줄은 단계(발현 준비 → 측정 준비 → 발현 → 분석 → 페그 조절)가 세로로 펼쳐진다.
- **색은 줄이 아니라 상태를 뜻한다.** 대기(베이지) · 진행 중(파랑) · 일시정지(호박색) · 성공(초록) · 실패(적갈색). 카드 머리에 범례가 있다. 페그 등록 중은 황동색.

### 3.2 그 밖에

- 따뜻한 악기 톤(크림·호두나무·황동), 밝은/어두운 테마(◐ 버튼).
- 글꼴은 **인터넷 없이 뜨도록 파일로 동봉**했다. 나눔스퀘어라운드(본문) · 나눔명조(로고·제목·음이름) · Nunito(숫자). 모두 무료 공개 라이선스(OFL)이고 라이선스 파일도 같이 넣었다.
- 문구: 로고 옆 "로봇 기타 자동 조율 시스템", 안내 "페그 재등록 후 시작하세요.", 작업 이력 "새로고침".
- 설정 5칸이 한 줄에 들어간다. 하단 설명 문단은 뺐다.
- 작업 이력의 판정 선택 칸 화살표를 끝에서 안쪽으로 옮겼다.
- 브라우저 탭 아이콘: 🎸(일렉기타로 보임) → 기타 헤드와 페그 6개 그림.
- 폰 너비에서도 깨지지 않는다(줄 블록 2×2).

## 4. 페그 효율 자동 보정 (#108)

### 4.1 왜 필요한가

`peg_calibration.yaml` 에는 "페그를 1도 돌리면 몇 센트 오른다" 가 적혀 있다. 그런데 실측(`docs/peg_data`)을 보면 줄마다 **그만큼 안 움직인다.**

- 2번 줄: yaml 1.065 센트/도, 실제 약 0.76 → **71%**
- 1번 줄: yaml 0.502, 실제 약 0.40 → **80%**
- 5번 줄: 거의 맞다

그래서 계산대로 돌려도 모자라 "조였는데 또 조이는" 일이 반복됐다.

### 4.2 어떻게 하나

1. 조절 한 번 뒤 다시 잰 음으로 **"예상보다 몇 %나 움직였나"** 를 본다.
2. 그 비율(효율)을 줄마다 기억해 **다음 조절 각도를 그만큼 늘리거나 줄인다.**
   - 예: 2번 줄을 30센트 올리려고 28도 돌렸는데 22.5센트만 올랐다(75%) → 효율 0.875 를 배우고, 다음엔 같은 오차에 1/0.875 배 더 돌린다.
3. 안전장치
   - "조임 한 번" 짜리 조절에서만 배운다. 풀기 → 조임은 백래시가 섞여 비율을 알 수 없다.
   - 3센트 미만 변화나 반대 방향 변화는 무시한다(측정 흔들림).
   - 효율은 0.5 ~ 1.5 배 사이로 제한한다. 새 관측은 절반만 반영한다.
   - **작업마다 1.0 에서 새로 배운다.** yaml 은 바꾸지 않는다.
4. 조절마다 기록을 남긴다: `~/.tunio/server_data/<작업ID>_peg_adjust.json`
   - 예상 변화 / 실제 변화 / 쓴 효율 / 배운 효율. 기록이 쌓이면 **사람이 yaml 값을 고치는 근거**로 쓴다.

위 숫자(0.5~1.5, 절반 반영, 3센트)는 전부 실측 전 임시값이다.

### 4.3 끄는 법 (스위치 `adaptive_gain`)

- **실행 중에 끄기** — 재시작 없이 다음 조절부터 적용
  ```bash
  ros2 param set /task_manager adaptive_gain false
  ros2 param get /task_manager adaptive_gain     # 확인
  ```
- **처음부터 끄고 띄우기** — `station` · `real_all` · `server` 런치 모두
  ```bash
  ros2 launch tunio_bringup station.launch.py device:=2 adaptive_gain:=false
  ```
- 끄면 yaml 값 그대로 돌린다(예전 동작). **배우기와 기록은 계속한다.** 끈 동안에도 배운 값이 지워지지 않아, 다시 켜면 이어서 쓴다.
- 기본값은 켜짐. Docker 에서 기본값 · 실행 중 끄고 켜기 · 런치 인자를 확인했다.

### 4.4 아직 안 맞는 것

- 웹의 "예상 페그 회전" 은 **yaml 값 기준**이다. 보정이 배우면 화면 각도와 실제 각도가 달라진다. 화면에 배운 값을 넘기는 건 후속 과제.

## 5. Docker 테스트와 여기서 고친 것

우분투 PC 없이 맥의 Docker 안에 **ROS 2 Jazzy** 를 띄워 확인했다. 두산 메시지 패키지(`dsr_msgs2`)는 공개 저장소에서 받아 같이 빌드했다.

결과
- `colcon build` 5개 패키지 성공.
- `colcon test` 688개 중 **환경 탓 2개만 실패** — 두산 파이썬 라이브러리 없음, 컨테이너가 root 라 생긴 차이. main 에서도 똑같이 실패한다.
- 가짜 하드웨어(`sim_all`)로 웹을 띄워 재등록 → 시작 → 일시정지(멈춤 유지) → 재개(이어서 진행) → 취소를 눌러 봤다.

테스트로 찾아 고친 것
1. **취소 시 정지 명령을 못 보내고 포기할 수 있었다 (실제 동작 수정)** — 두산 정지 서비스 연결을 한 번만 보고 포기하던 것을, 제한 시간 안에서 다시 확인하게 했다. 9/23 과 같은 종류의 문제다.
2. **로봇이 요청을 받다가 응답 없이 멈출 수 있었다 (실제 동작 수정)** — 정지 서비스 연결이 아예 없으면 에러로 멈추는 대신 "정지/상태 서비스 미연결" 이유로 거부한다. 실제 운용에서는 거의 안 생기는 경우지만 막았다.
3. **#88 통합 테스트 24개가 합친 뒤 전부 실패** — 테스트 환경에 두산 정지 서비스가 없어서였다. 가짜 서비스를 넣자 전부 통과. 2.3 의 연결이 실제 ROS 통신 위에서 돈다는 확인이다.
4. 테스트 속 가짜 노드에 상대 PR 이 새로 쓰는 값이 빠져 있던 것 (#106 · #88 테스트 각 1개). 테스트만 수정.
5. 코드 스타일 검사(flake8) 6곳 — 문서 문자열 마침표, import 순서. 안 고치면 우분투 `colcon test` 가 빨갛게 뜬다.

전체 테스트를 한꺼번에 돌리면 ROS 통합 테스트 1개가 가끔 "노드 찾기 5초 초과" 로 실패한다. 따로 반복하면 매번 통과한다. 컨테이너가 바쁠 때의 타이밍 문제로 본다.
